### 2.2 阶段判断矩阵

根据扫描结果，对照以下矩阵判断当前阶段，**选择最符合的阶段**：

```

    - pyproject.toml 不存在

  进入：第三部分 → 阶段 0 任务

阶段 1：核心引擎建设
  判断条件：
    - pyproject.toml 存在
    - src/echoui/ 存在
    - src/echoui/core/ 下缺少任意一个文件
    - 或 src/echoui/utils/ 下缺少任意一个文件
  进入：第三部分 → 阶段 1 任务

阶段 2：组件库建设
  判断条件：
    - 所有 core/ 文件存在
    - 所有 utils/ 文件存在
    - components/ 下缺少任意一个文件

  进入：第三部分 → 阶段 2 任务

阶段 3：测试补全
  判断条件：
    - 所有源码文件存在
    - tests/ 下文件数 < 15

  进入：第三部分 → 阶段 3 任务

阶段 4：自检与修复
  判断条件：
    - 所有源码文件存在
    - tests/ 下文件数 >= 15
    - 测试全部通过
    - 但覆盖率仍未达标
    - 或存在 lint/type 错误
  进入：第三部分 → 阶段 4 任务

阶段 5：完成验证
  判断条件：
    - 所有源码文件存在
    - 所有测试通过
    - 所有覆盖率达标（core>=95%, components>=90%, utils>=90%, 整体>=90%）
    - mypy 无报错
    - pylint 无严重错误
  进入：第三部分 → 阶段 5 任务

## 五、多轮循环说明（给 Agent 的提示）

本文件（TASK.txt）设计为多轮循环使用。每次收到本文件时：

```
第 1 轮收到 TASK.txt：
  → 执行第一步（读取规范）
  → 执行第二步（扫描项目，判断为阶段 0）
  → 执行阶段 0 任务（初始化项目结构）
  → 执行第四步（记录进度）

第 2 轮收到 TASK.txt：
  → 执行第一步（重新读取规范，刷新记忆）
  → 执行第二步（扫描项目，判断为阶段 1）
  → 执行阶段 1 任务（实现核心引擎）
  → 执行第四步

第 3-N 轮收到 TASK.txt：
  → 重复上述流程，阶段递进
  → 直到阶段 5 完成，最终状态报告显示全部达标
```

**关键原则**:

```
1. 每次收到 TASK.txt，必须重新读取规范文件（不依赖上次的记忆）
2. 每次必须重新扫描项目状态（不假设上次的状态不变）
3. 每次必须从最低未完成阶段开始（不跳过阶段）
4. 每次结束前必须更新 AGENTS.md
5. 如果一个阶段在单次会话中无法完全完成，记录进度后下次继续
6. 同一阶段可能跨越多次会话，直到所有检查项通过
```

## 六、紧急情况处理

### 6.1 发现代码库已有但不符合规范的文件

```
处理流程：
1. 不得删除，先读取理解现有实现意图
2. 识别具体的规范违反点
3. 告知开发者："发现文件 {路径} 存在以下规范问题：{列表}"
4. 制定修复计划，按优先级逐步修复
5. 修复后记录到 AGENTS.md
```

### 6.2 发现循环导入

```
处理流程：
1. 使用 TYPE_CHECKING 块隔离仅类型检查时需要的导入
2. 重构模块依赖关系（被依赖的模块不得反向导入依赖它的模块）
3. 如果无法避免，将共享类型定义提取到独立的 types.py 文件
4. 记录到 AGENTS.md
```

### 6.3 发现测试无法通过且原因不明

```
处理流程：
1. 隔离问题：pytest {具体测试文件}::{具体测试方法} -v -s
2. 添加临时调试 logging（不是 print）
3. 分析是实现问题还是测试问题
4. 修复实现（优先），或修复测试（如果测试假设确实有误）
5. 绝不注释掉测试来让覆盖率通过
6. 记录到 AGENTS.md
```

### 6.4 文件超出行数限制

```
处理流程：
1. 识别可以提取的功能单元（辅助函数、内部类、工具方法）
2. 创建新文件（命名为 {原文件名}_{功能}.py）
3. 迁移代码，更新导入
4. 验证测试仍然通过
5. 如果是测试文件超长，按测试类拆分到子文件
```
